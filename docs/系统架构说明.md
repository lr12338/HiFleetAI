# 系统架构说明

## 1. 架构目标

HiFleetAI 当前架构的目标是先建立一个可测试、可交付、可扩展的客服 Agent 平台基线，而不是一次性做成完整多渠道生产系统。

架构设计强调：

- 前端后台与后续渠道统一走后端 API
- 聊天入口统一收敛到 `/api/v1/chat`
- 路由、模型、会话、Harness 明确分层
- 所有关键链路都能被 `pytest` 和 Harness 验证

## 2. 当前总体结构

```mermaid
flowchart LR
    FE[前端管理后台] --> AUTH[/api/v1/auth/*/]
    FE --> CONV[/api/v1/conversations/*/]
    FE --> HARNESS[/api/v1/harness/runs*]
    FE --> CHAT[/api/v1/chat]

    CHAT --> SUPERVISOR[SupervisorRouter]
    CHAT --> GATEWAY[ModelGateway]
    CHAT --> CONV_SERVICE[ConversationService]

    SUPERVISOR --> FAQ[FAQ 路由]
    SUPERVISOR --> SKILL[Skill 候选路由]
    SUPERVISOR --> WEB[网页检索占位]
    SUPERVISOR --> IMAGE[图片理解占位]
    SUPERVISOR --> HANDOFF[人工接管路由]

    CONV_SERVICE --> DB[(SQLite 或 PostgreSQL)]

    HARNESS_RUNNER[Harness Runner] --> CHAT
    HARNESS_RUNNER --> HANDOFF_API[handoff API]
    HARNESS --> HARNESS_SERVICE[HarnessResultService]
    HARNESS_SERVICE --> REPORTS[harness/reports/latest.*]
```

## 3. 后端结构

### 3.1 API 层

后端入口在 `backend/app/main.py`，统一通过 `backend/app/api/__init__.py` 注册版本化路由。

当前关键接口：

- `GET /api/health`
- `POST /api/v1/auth/login`
- `GET /api/v1/auth/me`
- `POST /api/v1/chat`
- `GET /api/v1/conversations`
- `GET /api/v1/conversations/{id}`
- `POST /api/v1/conversations/{id}/notes`
- `POST /api/v1/conversations/{id}/handoff`
- `POST /api/v1/conversations/{id}/pause-ai`
- `POST /api/v1/conversations/{id}/resume-ai`
- `GET /api/v1/harness/runs`
- `GET /api/v1/harness/runs/{id}`

### 3.2 聊天入口

`/api/v1/chat` 是当前统一聊天入口，也是 Harness `regression` 直接调用的主链路。

当前已实现：

- 标准化输入结构
- `SupervisorRouter` 规则优先路由
- FAQ / Skill / Handoff / General Chat 的最小分流
- `ModelGateway` 文本模型调用
- 会话、消息、工具调用、模型调用的 best-effort 落库

当前未实现：

- 真实知识库检索执行
- 真实网页检索执行
- 真实多模态应用内推理
- 真实生产 Skill 服务调用
- 生产级多轮编排

## 4. 路由与模型层

### 4.1 SupervisorRouter

`backend/app/agent/supervisor.py` 负责最小规则优先路由。当前可识别：

- FAQ
- Skill 候选
- Web Research
- Image Understanding
- Handoff Required
- General Chat

它负责决定走哪条链路，不直接承担所有能力执行。

### 4.2 ModelGateway

`backend/app/agent/model_gateway.py` 负责统一模型提供方接口。当前支持：

- `fake`：本地测试用假模型
- `ark`：火山 Ark 文本请求

最近一轮系统验证已确认：

- Ark 文本链路在系统内可用
- 多模态当前只完成 Ark 直连验证，未接入 `/api/v1/chat`

## 5. 会话域结构

`backend/app/services/conversation_service.py` 负责：

- 创建与读取会话
- 追加消息
- 管理内部备注
- 管理 handoff / pause-ai / resume-ai 状态迁移
- 读取工具调用和错误上下文

当前数据库模型覆盖：

- `conversations`
- `messages`
- `model_calls`
- `tool_calls`
- `handoff_events`
- `conversation_notes`
- `harness_runs`
- `harness_results`

## 6. 前端结构

前端位于 `frontend/`，技术栈为 React + Vite + TypeScript。

当前页面：

- 登录页
- 会话列表页
- 会话详情页
- Harness 结果页
- Test Chat 页面

当前依赖的关键后端能力：

- 登录认证
- 会话列表与详情
- 备注、接管、AI 状态流转
- Harness 结果查询
- `/api/v1/chat`

## 7. Harness 结构

Harness 位于 `harness/`，当前分为：

- `cases/`：分类测试用例
- `runners/run_eval.py`：执行入口
- `judges/deterministic_judge.py`：确定性判断器
- `reports/latest.json` / `latest.md`：最近一次结果

当前运行特点：

- `handoff` 通过进程内 API 链路验证状态流转
- `regression` 通过真实 HTTP 调用 `/api/v1/chat`
- `latest.*` 每次运行都会覆盖

## 8. 当前环境边界

最新验证确认：

- SQLite 路径下，前后端与 Harness 主链路均可运行
- PostgreSQL 应用内验证仍被当前环境的 `psycopg` 运行时问题阻塞
- Docker 权限不足会影响通过 Compose 自举基础设施
- `HiFleetData/` 仍未接入真实知识检索链路

## 9. 后续架构演进建议

进入 Phase 3 时，应保持当前分层，不要把新能力直接堆回：

- 前端页面
- `/api/v1/chat` 单文件逻辑
- Prompt 文本

更合理的方向是继续保持：

- 渠道适配层独立
- 知识库能力独立
- Skill 执行层独立
- Harness 继续作为回归收口标准
