# 开发规范

## 1. 适用范围

本文档适用于 HiFleetAI 当前 Phase 0 至 Phase 2 收口后的持续维护与后续阶段开发，统一收敛以下内容：

- Harness 驱动开发原则
- 版本与提交规则
- Agent 协作规则
- 禁止提交内容

## 2. 核心原则

### 2.1 证据优先

任何功能、修复、重构、交付都必须有对应证据：

- `pytest`
- Harness
- 可执行验证命令
- 或明确记录的环境阻塞

### 2.2 不伪造成功

不得伪造以下内容：

- 模型调用成功
- 知识库检索成功
- Skill 执行成功
- 数据库或对象存储可用
- Harness 通过

### 2.3 统一入口

聊天能力统一通过：

- `/api/v1/chat`

不得在新任务中绕开统一入口，将渠道逻辑或业务执行逻辑直接写死到前端或临时脚本中。

### 2.4 不扩大当前范围

在明确进入下一阶段前，不得擅自扩展到：

- 微信公众号真实接入
- Chatwoot 真实接入
- 微信客服平台真实接入
- 文件分析沙箱
- 订阅通知
- 高风险生产写操作

## 3. Agent 协作规则

### 3.1 主控与子任务

- 一个子 Agent 只执行一个明确任务
- 每个任务都应映射到需求章节和任务编号
- 子任务完成前必须运行对应验收命令

### 3.2 开工前说明

开始改动前应先明确：

- 任务编号与任务名
- 目标
- 涉及文件
- 不在范围内的内容
- 对应测试或验证方式

### 3.3 完成前要求

任务进入完成或评审前，必须：

- 跑完验收命令
- 记录结果
- 明确修改文件
- 明确失败项和环境阻塞

## 4. 分支与提交规范

### 4.1 分支命名

推荐：

- `main`
- `feature/<task-id>-<short-name>`
- `fix/<task-id>-<short-name>`
- `docs/<short-name>`

### 4.2 提交格式

统一格式：

```text
<type>(<scope>): <summary>
```

允许类型：

- `feat`
- `fix`
- `docs`
- `test`
- `chore`
- `refactor`

示例：

- `docs(project): reorganize documentation structure`
- `test(chat): validate regression and faq flows`
- `fix(auth): restore local admin bootstrap path`

### 4.3 提交边界

一条提交应尽量对应一类清晰改动，不要混入：

- 无关依赖安装
- 运行产物
- 大量格式化噪音
- 无关模块的行为改动

## 5. 测试与 Harness 规则

### 5.1 自动化优先

建议顺序：

1. 后端专项测试
2. 后端全量 `pytest`
3. 前端 `npm test`
4. 前端 `npm run build`
5. Harness `handoff`
6. Harness `regression`

### 5.2 Harness 规则

- `handoff` 用于验证状态流转
- `regression` 用于验证 `/api/v1/chat` 契约不退化
- `latest.*` 只代表最近一次执行结果，不能当作稳定交付物提交

## 6. 文档规则

- 所有主文档统一中文
- 主文档按用途分层，不混写方案、测试、日志、交接
- 日志只承担过程记录，不承担主说明职责
- 若历史文档仍有价值，优先归档而不是直接丢弃

## 7. 禁止提交的内容

以下内容不得进入版本控制：

- `.env`
- 真实 API key、token、cookie、私钥
- `.venv/`
- `node_modules/`
- `dist/`
- 运行日志
- 上传文件
- 临时缓存
- `harness/reports/latest.json`
- `harness/reports/latest.md`
- `HiFleetData/`

## 8. 当前环境事实

根据最新系统验证，当前必须特别注意：

- SQLite 路径是最近一轮已验证可复现基线
- PostgreSQL 应用内验证仍受 `psycopg` 运行时阻塞
- Docker Compose 自举受 Docker 权限限制
- 知识库真实接入链路尚未完成

## 9. 建议的开发顺序

对后续开发，建议始终按以下顺序推进：

1. 先读文档
2. 先看工作树
3. 先跑验证
4. 再拆任务
5. 再补测试或 Harness
6. 最后做最小实现与收口
