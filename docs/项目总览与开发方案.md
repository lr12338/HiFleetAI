# 项目总览与开发方案

## 1. 项目定位

HiFleetAI 是一个面向企业客服场景的 Agent 平台。当前阶段的核心目标不是一次性接入所有真实渠道，而是先形成一个可验证、可回归、可持续演进的标准客服后台 MVP。

当前交付重点：

- 自建标准客服后台
- 统一 Agent API：`/api/v1/chat`
- 会话、备注、人工接管与 AI 状态管理
- Harness 驱动的回归测试体系

## 2. 当前范围

当前代码基线已经完成 Phase 0、Phase 1、Phase 2，并补齐了本地完整体验闭环。

已完成范围：

- 登录与鉴权
- 会话列表与会话详情
- 人工接管、AI 暂停、AI 恢复
- 内部备注
- Harness 结果页
- `/api/v1/chat` 最小响应契约
- 前端 `Test Chat` 页面
- Ark 文本模型调用链路

当前明确不在范围内：

- 微信公众号真实接入
- Chatwoot 真实接入
- 微信客服平台真实接入
- 真实网页检索执行
- 真实多模态应用内执行
- 真实业务 Skill 服务接入
- 文件分析沙箱
- 高风险生产写操作

## 3. 当前阶段判断

当前系统处于：

- Phase 2 已完成收口
- 本地完整体验闭环已补齐
- 准备进入 Phase 3 规划，而不是继续扩展 Phase 2

如果你刚接手项目，应优先理解当前已交付基线与环境边界，而不是直接进入新功能开发。

## 4. 目录结构


## 6. 当前开发原则

- 统一通过 `/api/v1/chat` 暴露聊天能力
- 自动化验证优先，手工联调补充
- 不伪造外部依赖成功
- 不把本地数据、密钥、缓存、报告文件混入版本控制
- 不在未完成规划时直接扩大 MVP 范围

## 7. 当前已知环境边界

根据最近一轮系统验证，当前项目存在以下环境级事实：

- 本地 SQLite 基线可完成完整联调
- Ark 文本模型链路可用
- PostgreSQL 应用内验证仍受 `psycopg` 运行时依赖阻塞
- Docker Compose 自举受当前账号 Docker 权限限制
- MinIO 未在最近一轮系统验证中成功启动
- `HiFleetData/` 目前仍未真正接入知识库检索链路

## 8. 后续开发建议

进入下一阶段前，建议优先处理三类问题：

1. 先巩固环境：补齐 PostgreSQL 驱动、Docker 权限、MinIO 可用性
2. 再补能力：明确知识库导入/索引/检索链路
3. 最后扩范围：按 Phase 3 规划拆解渠道接入任务
